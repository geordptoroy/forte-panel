# O2.3 — Outbound com `instanceId`, fila e reconciliação

**Data:** 2026-10-01
**Estado:** implementada e validada com testes de contrato; processamento com PostgreSQL e gateway real continua pendente

## Auditoria

O outbound do Panel já usa uma mensagem persistida como unidade de trabalho. O Inbox cria mensagens com status `queued`, o worker faz claim condicional de `queued` para `processing`, usa `forte-message-{message.id}` como chave estável de idempotência e envia pelo adapter Baileys. Em sucesso, grava `status = sent`, `externalId` e `sentAt`; em falha, preserva `lastError`, incrementa tentativas e retorna a mensagem para `queued` até `WORKER_MAX_ATTEMPTS`, quando passa a `failed`. O boot do worker recupera mensagens que ficaram em `processing`.

A resposta do gateway é reconciliada na mesma linha por `externalId`, e um evento de domínio `message.sent` é enfileirado para auditoria/consumidores posteriores. O estado persistido (`queued`, `processing`, `sent`, `failed`) já é o estado exibido pelo Inbox e pelo pipeline operacional, sem afirmar entrega quando há apenas enfileiramento.

O adapter preserva o JID de origem quando disponível, envia sempre para `/api/instances/{instanceId}/send`, inclui a chave `Idempotency-Key` e falha fechado se não houver `instanceId`. Não existe fallback global para a instância default.

## Correções desta fatia

### InstanceId obrigatório na entrada

A API REST agora responde `400 instance_id_required` antes de criar contato ou mensagem quando um envio Baileys não informa `instanceId`. O mesmo contrato vale para cada item de `/messages/batch`. A camada de banco também impõe a regra para chamadas internas, evitando que qualquer caller crie uma mensagem que só descobriria o erro no worker.

O envio manual do Inbox também falha fechado quando não consegue resolver uma única conexão: exige a instância registrada na origem da conversa ou uma seleção única feita pelo operador. Seleções múltiplas continuam adequadas para filtro de Inbox, mas não para decidir o destino de uma resposta.

### Cota depois do claim

O worker agora disputa o claim da mensagem antes de consumir a cota outbound. Se outro worker ganhou a mesma mensagem, o segundo não debita cota. Quando a cota está esgotada, o claim é devolvido a `queued` sem aumentar `attemptCount`. Somente mensagens realmente autorizadas para tentativa avançam o contador e seguem ao gateway.

## Reconciliação e limites preservados

Uma requisição aceita pela API significa apenas `queued`; envio confirmado exige `sent` com `externalId`. Falhas do gateway não são convertidas em sucesso. A chave estável por ID da mensagem permite reexecução do worker; o gateway recebe essa chave em todas as tentativas. A deduplicação definitiva de uma tentativa que caiu depois do envio depende da capacidade de idempotência/reconciliação do gateway e deve ser validada no Docker com um caso de timeout real.

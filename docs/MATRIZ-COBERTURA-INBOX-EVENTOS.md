# Matriz de cobertura — eventos da Inbox Forte

## Escopo e metodologia

Esta matriz sintetiza **apenas os resultados estruturados fornecidos** para o commit `db51134abe5bad57bbb5e420b8047ae425746b92`, na branch `feat/o7.15-storage-reconciliation-observability`. A inspeção dos eventos foi **read-only quanto ao código de produto**; esta matriz foi criada como artefacto documental. Não foram fornecidos resultados falhados (`failures: []`).

A cobertura é separada por evento e por etapa do percurso **socket/bridge → webhook → normalização → persistência → Inbox**. «Confirmado» significa que o resultado cita implementação ou teste correspondente; «parcial» significa que só existe suporte adjacente ou para outra forma do evento; «não confirmado» preserva explicitamente a lacuna da auditoria; «indisponível no caminho auditado» significa que não foi encontrado entrypoint/handler implementado para esse evento no código verificado. A ausência de teste ou de evidência não é convertida em afirmação de inexistência fora do código auditado. As referências são mantidas no formato `arquivo:linha` (ou `arquivo:Lx-Ly`, quando assim fornecidas).

## Lacunas e bloqueadores

1. **Segredos e estado do deployment:** a configuração efetiva de segredos, URLs, workspace, instâncias ativas, rotação e execução real não foi inspecionada; permanece **não confirmada** para os eventos em que isso foi indicado.
2. **Percurso E2E:** não foi encontrado nem executado um teste único que cubra socket → assinatura/autenticação → API → PostgreSQL → router/UI. A ausência de evidência de teste não é evidência de ausência de suporte.
3. **Histórico/backfill:** `messaging-history.set` é explicitamente ignorado pela rota ativa com `202 ignored` antes de tenancy/ledger/ingestão. Existe função de DB e documentação que descrevem importação, mas a documentação diverge do handler observado; não se deve inferir que a importação esteja operacional.
4. **Receipts antes do vínculo do ID:** para `messages.update`, o buffer é volátil, limitado a 120 segundos/256 IDs; persistência/recuperação após reinício não está evidenciada.
5. **Eventos sem handler observado:** `chats.update`, `contacts.update`, `presence.update`, `groups.update`, `group-participants.update` e `labels` estão indisponíveis ou não confirmados no caminho auditado. Os mecanismos genéricos de mensagens/webhooks não foram promovidos a cobertura desses eventos.
6. **Reações:** há suporte parcial a `reactionMessage` dentro de `messages.upsert` e ao tipo `react`, mas não há evidência do evento nomeado `messages.reaction`, de associação à mensagem-alvo ou de preservação do payload estruturado no adapter.
7. **Grupos e contactos:** nomes, subjects e participantes podem ser observados incidentalmente ao processar mensagens; isso não comprova sincronização por eventos de atualização dedicados.
8. **Labels:** a documentação PAPI é apenas referência de eventos e não demonstra implementação Forte; não foi encontrada entidade de armazenamento, contrato, listener ou UI específicos.
9. **Testes condicionais:** alguns testes dependem de `DATABASE_URL`; o resultado fornecido indica que não foram executados nesta auditoria. Não há resultados de execução a usar como prova operacional.
10. **Concorrência:** não foi encontrado E2E da corrida simultânea de entrega/ingestão no percurso completo de `messages.upsert`; a existência de leases/índices não deve ser apresentada como validação E2E.
